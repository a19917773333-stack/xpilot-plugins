# Main-road merge and lane-position gaps

User reports: a navigation preparation lamp was cancelled again, and a later
main-road instruction caused another lane change after already entering the main road.
The device was unavailable, so the latest trip has not been read and these mechanisms
are not claimed as the proven cause of that specific trip.

Two source-level paths were reproduced and corrected:

- `mergeLeft` / `mergeRight` previously permitted a direction-only edge search.
  They now require confirmed absolute lane membership and explicit recommendations.
  Already occupying a recommended lane produces no lane request. A confirmed mismatch
  can still request an adjacent step under the existing native crossing/BSM gates.
  This does not infer main-road membership from words or from road direction.
- A fresh navigation event with briefly unavailable map-to-visual position previously
  entered recovery by immediately releasing the lamp. It now uses the existing bounded
  one-second observation grace, retaining the request ID while clearing readiness.
  Stable recovery and crossing/physical-lamp confirmation must run again. Longer loss
  releases the lamp and enters the existing three-second, limited-retry recovery.

Route changes, stale navigation, driver override, the overall 60-second preparation
budget, BSM and boundary checks retain their stop/release behavior. This is not an
unlimited lamp latch and does not preserve stale permission to steer.

Validation: regression contracts were recorded before implementation; 547 plugin tests
pass, including the short-gap, missing-position, merge-membership and override cases.
The real host store installs/discovers the portable archive set. Device activation and
the latest-trip verification remain pending. The fix belongs to both X-Pilot profiles;
the legacy running checkout has not been modified.
